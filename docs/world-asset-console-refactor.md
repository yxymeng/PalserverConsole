# 世界资产台完全重构规格

- 状态：Accepted
- 确认日期：2026-08-20
- 访客模式：Operate
- 目标入口：`世界数据`
- 主要实现入口：`frontend/src/features/world/WorldDataPage.tsx`
- 领域语言：[CONTEXT.md](../CONTEXT.md)
- 架构决策：[ADR-0001](adr/0001-world-asset-console.md)

## 1. 目标

将现有通用实体浏览器重构为管理员使用的只读“世界资产台”。管理员进入页面后应能快速回答：

1. 当前存档快照是否可信、是否过期；
2. 世界中有哪些玩家、帕鲁、物资、据点和公会；
3. 资产在哪里、属于谁、彼此如何关联；
4. 哪些帕鲁需要关注；
5. 玩家完成了哪些主要探索与战斗进度。

参考项目为 [yxymeng/palworld-panel](https://github.com/yxymeng/palworld-panel) 的仓库与帕鲁页面。只借鉴信息组织、聚合方式、筛选能力和详情层级，不复制来源或许可不清的代码、数据与素材。

## 2. 范围

本次是完整的只读全栈重构，范围包括：

- 存档字段解析；
- 派生 SQLite 世界缓存；
- 只读查询 API；
- 世界资产台前端；
- 合成、脱敏和只读验证；
- 许可与第三方 notice；
- 桌面和移动端验收。

### 2.1 明确不做

- 不修改真实 `.sav`；
- 不增加据点改名、治疗、移动物品、删除资产等写操作；
- 不增加恢复、配置覆盖、服务器生命周期或维护动作；
- 不把存档状态描述为实时状态；
- 不把玩家坐标、原始完成 Flag 或长内部 ID 作为主要内容；
- 不重构首页、配置或维护页面；
- 不更换项目全局视觉体系；
- 不在运行时联网获取游戏元数据；
- 不在本模块中执行 commit、push、PR、Release。

## 3. 信息架构

保留一级入口 `世界数据`，内部二级入口固定为：

1. `总览`
2. `玩家`
3. `帕鲁名册`
4. `仓库`
5. `据点`
6. `公会`

默认进入 `总览`。关系跳转应进入对应二级入口和筛选结果，而不是展示孤立技术记录。

## 4. 选定结构：总览门厅

视觉体系继承当前 ZOE 浅雾蓝 light/dark 设计。页面结构采用“总览门厅”：先建立全局认知，再进入专项工作区。

### 4.1 第一视口

第一视口按以下顺序组织：

1. 紧凑存档快照条；
2. 二级导航；
3. 玩家、帕鲁、物品种类、据点、公会等资产规模；
4. 照护摘要、稀有帕鲁摘要和数据完整性；
5. 进入专项筛选结果的直接入口。

首屏不得被内部 ID、技术计数、大段解析说明或完整实体列表占据。

### 4.2 视觉约束

- 沿用 `DESIGN.md` 的近白画布、浅雾蓝交互色、青绿健康状态和珊瑚红危险状态；
- 不照搬参考项目的深色 HUD、小字号、霓虹或高压密度；
- 个体标记、资质和照护状态必须使用不同的信息层级；
- 状态不能只用颜色表达；
- 详情仍使用桌面右侧抽屉和移动端全屏层；
- 内部 ID 默认弱化或折叠。

## 5. 存档快照条

快照条始终明确展示：

- 存档记录时间；
- 解析完成时间；
- 当前是否正在解析；
- 是否正在显示最后成功缓存；
- 解析失败的可复制英文错误标识与中文说明；
- `重新解析` 入口。

快照条必须紧凑，不重复总览统计。解析失败但存在成功缓存时继续提供旧数据，并持续标明 `stale`；没有成功缓存时进入明确的不可用状态。

帕鲁活动、疾病、饱食度、SAN 和生命值均来自存档快照，不得描述为实时监控结果。

## 6. 总览

总览只承担三类信息：

### 6.1 快照可信度

- 当前快照是否可用；
- 是否过期或解析失败；
- 数据覆盖是否完整。

### 6.2 资产规模

- 玩家数量；
- 帕鲁总数与物种数；
- 物品种类与物品总量；
- 据点数量；
- 公会数量。

### 6.3 需要处理或进一步查看的事项

- 需要关注的帕鲁数量；
- 闪光帕鲁数量；
- 头目帕鲁数量；
- 未归属帕鲁数量；
- 未识别物品或元数据缺口；
- 解析完整性警告。

每个摘要都应能进入对应二级入口和已应用的筛选条件。总览不展示大段世界进度、完整列表或仅供开发者使用的 Actor、容器、Flag 技术计数；技术诊断放入次要展开区。

## 7. 帕鲁名册

### 7.1 默认表达

帕鲁名册使用稳定的均衡列表，不因照护异常自动改变默认顺序。桌面列表优先展示：

- 头像、名称与性别；
- 等级与星级；
- 闪光、头目等个体标记；
- 玩家、队伍、终端或据点归属；
- 生命/攻击/防御个体值摘要；
- 主要工作适应性；
- 主要被动技能；
- 照护状态摘要。

移动端改为纵向卡片，保持相同能力，但减少同屏字段；高级信息进入展开或详情，不缩小桌面表格。

### 7.2 筛选与排序

常用快捷筛选：

- 全部；
- 需要关注；
- 闪光；
- 头目。

高级筛选：

- 玩家或据点归属；
- 工作适应性及最低等级，多项选择按“全部具备”解释；
- 被动技能，多项选择按“全部具备”解释；
- 最低等级；
- 最低星级；
- 生命、攻击、防御和平均个体值；
- 物种稀有度。

排序至少包括名称、等级、平均个体值和工作适应性。已应用筛选使用可单独移除的筛选标签表达。

### 7.3 浏览规模

- 查询、筛选和排序在服务端完成；
- 首次约返回 60 条；
- 使用“加载更多”，不一次渲染全部帕鲁；
- 返回列表时恢复筛选条件、已加载结果和滚动位置；
- 新快照切换后应明确刷新结果，不能把不同快照的数据静默拼接。

### 7.4 帕鲁详情

桌面使用全高右侧抽屉，移动端使用全屏详情层。内容顺序固定为：

1. 身份与归属；
2. 照护状态；
3. 等级、星级和基础属性；
4. 个体值；
5. 工作适应性；
6. 被动技能；
7. 已装备主动技能；
8. 已掌握主动技能；
9. 伙伴技能；
10. 折叠的技术信息。

从详情跳转玩家或据点后必须保留可返回路径与原列表状态。

## 8. 帕鲁照护状态

个体标记、资质和照护状态不得混为一个“状态”字段。

### 8.1 需要关注

`Critical`：

- 当前生命值为零；
- 存档包含明确疾病。

`Warning`：

- 饱食度低于 20%；
- SAN 低于 50%。

`Info`：

- 工作中；
- 休息；
- 偷懒或其他存档活动事件。

`Info` 不计入“需要关注”。同一只帕鲁可以同时具有多个关注原因。字段缺失显示“数据不可用”，不得推断为健康。

### 8.2 疾病

已知疾病应显示具体中文名称，例如感冒、扭伤、胃溃疡、骨折、虚弱、抑郁症和暴食症。遇到未知枚举值时显示稳定的原始枚举与“资料未收录”，不得丢弃。

## 9. 仓库

仓库只表示物品与材料，不表示帕鲁终端。

### 9.1 聚合模型

- 默认按物品聚合整个世界的总量；
- 同一物品的玩家背包与据点库存合并为一个物品条目；
- 展开条目后按玩家/据点和容器位置列出数量与槽位；
- 玩家和据点详情可以进入只显示该归属范围的仓库结果。

### 9.2 查询

支持：

- 中文名称或内部 Item ID 搜索；
- 物品分类筛选；
- 全部、玩家、据点快捷筛选；
- 指定玩家或据点筛选；
- 按名称和总量排序。

默认隐藏空槽和容器 ID。技术信息可在位置详情中折叠显示。未知物品必须保留真实数量和位置，并显示 Item ID 与“资料未收录”。

## 10. 玩家

玩家列表展示名称、等级、公会、帕鲁规模、主要进度摘要和数据覆盖状态。

### 10.1 玩家详情

- 等级、所属公会和最后记录时间；
- 队伍帕鲁与终端帕鲁入口；
- 玩家库存入口；
- 已发现帕鲁种类；
- 累计捕获帕鲁数量；
- 已解锁传送点；
- 已探索区域；
- 已完成野外头目项目；
- 已完成高塔；
- 地下城通关次数；
- 油田通关次数；
- 当前科技点与古代科技点；
- 已解锁配方数量。

### 10.2 进度语义

- `NormalBossDefeatFlag` 和 `TowerBossDefeatFlag` 统计完成标记数量，不描述为累计击杀次数；
- 地下城与油田使用存档中的累计通关计数；
- “发现帕鲁种类”与“累计捕获帕鲁数量”必须明确区分；
- 缺少玩家存档时显示“玩家进度不可用”，不返回一组假零值；
- 仅部分字段可用时显示“部分数据”并列出不可用项目；
- 不在主界面展示玩家精确坐标、原始 Flag 或长 ID。

## 11. 据点与公会

### 11.1 据点

据点详情展示：

- 名称与稳定 Base ID；
- 所属公会；
- 坐标；
- 工作帕鲁数量和照护摘要；
- 工作帕鲁入口；
- 据点库存入口。

不得按空间距离猜测据点、帕鲁或库存关系；只使用稳定 ID。

### 11.2 公会

公会详情展示：

- 名称与稳定 Guild ID；
- 成员列表；
- 据点列表；
- 成员、据点、帕鲁和仓库的聚合规模；
- 进入关联玩家、据点、帕鲁或仓库筛选结果的入口。

## 12. 元数据与许可

- 所有元数据在构建期或开发期从固定版本来源导入；
- 来源、固定 revision、用途和许可证写入 `THIRD_PARTY_NOTICES.md`；
- 运行时不请求远端元数据服务，不上传存档数据；
- 帕鲁继续使用项目现有、已归档许可的头像与中文目录；
- 新增技能、工作适应性和物品元数据必须有明确许可；
- 首版物品使用分类图标，不引入来源不清的游戏物品图片；
- 参考项目中没有明确许可链的索引不得直接复制。

## 13. 数据与 API 要求

- 派生缓存必须有显式 schema/version；
- 新字段上线时通过重新解析生成新缓存，不原地修改真实存档；
- 新缓存通过完整性检查后原子切换；
- 解析失败时继续保留最后成功缓存；
- 现有只读 `/api/world/...` 能力在迁移期间保持兼容，新增字段不得让旧调用方失效；
- 新列表响应应使用明确类型，不继续扩大无约束的 `Record<string, unknown>`；
- 过滤、排序、聚合在服务端执行；
- 列表与详情都带快照标识和时效信息，防止跨快照混用；
- 未识别数据保留原始 ID，不静默过滤；
- 所有 ID 关系由稳定 ID 建立，不按名称或距离猜测。

## 14. 状态矩阵

每个二级入口至少覆盖：

- 初次加载；
- 快速加载和延迟加载；
- 解析中；
- 当前快照可用；
- 旧缓存可用；
- 解析失败且旧缓存可用；
- 完全没有成功缓存；
- 无数据；
- 筛选无结果；
- 元数据未收录；
- 玩家进度完整；
- 玩家进度部分可用；
- 玩家进度不可用；
- 关联实体缺失；
- 加载更多失败；
- 桌面详情打开；
- 移动端详情打开。

错误状态保留关键英文 `errorCode` 或原始错误标识，并提供中文影响与下一步。

## 15. 响应式与可访问性

- 桌面端保留高密度共享轮廓列表；
- 移动端使用纵向卡片，不缩小桌面表格；
- 二级导航在窄屏横向滚动；
- 常用筛选直接显示，高级筛选进入全屏筛选层；
- 详情在移动端使用全屏层；
- 仓库位置展开在移动端仍可完整操作；
- 控件触控目标至少 40px；
- 支持键盘操作、明确焦点、Escape 关闭和焦点恢复；
- 状态不只依赖颜色；
- 尊重 `prefers-reduced-motion`；
- 长名称和内部 ID 不得造成横向溢出。

## 16. 性能基线

设计与测试至少覆盖以下量级：

- 0、少量和 200+ 玩家；
- 0、典型约 1,600 和压力 5,000 只帕鲁；
- 0、典型约 13,000 和压力 50,000 个物品槽；
- 多据点、多公会及缺失关系；
- 多条件筛选和加载更多。

物品槽必须先在服务端聚合，不能直接把全部槽位发送到首屏。前端不得一次创建全部帕鲁 DOM 节点。切换筛选或快照时必须取消或淘汰旧请求结果。

## 17. 验收标准

### 17.1 功能

- 六个二级入口均可访问；
- 总览摘要可进入对应筛选结果；
- 帕鲁快捷与高级筛选语义正确；
- 需要关注规则与严重级别正确；
- 仓库总量等于各位置数量之和；
- 玩家进度区分完成项目数与累计次数；
- 玩家、帕鲁、仓库、据点和公会关系可往返导航；
- 缺失与未知数据不显示假零值、不被静默丢弃；
- 重新解析不修改真实存档。

### 17.2 安全与数据完整性

- 真实验证只读，源存档哈希前后相同；
- 测试使用 mock、合成数据、脱敏 fixture 或临时副本；
- 前端、日志、测试输出和截图不包含真实玩家 ID、真实路径或未脱敏数据；
- 缓存切换失败时仍可读取旧成功缓存；
- 未增加任何世界写入 API。

### 17.3 前端

- 当前 ZOE light/dark 视觉体系保持一致；
- `1440x960` 桌面和 `390x844` 手机无横向溢出、遮挡和不可达控件；
- 列表返回可恢复状态；
- 抽屉焦点、Escape、遮罩和移动端滚动正确；
- loading、empty、error、stale 和 partial states 均有自动化或 E2E 覆盖；
- reduced-motion 下不依赖动画理解状态。

### 17.4 验证命令

实施模块应按影响运行：

- 后端相关 `pytest`；
- 后端全量 `pytest`、Ruff、mypy；
- 前端相关 Vitest；
- 前端 lint、typecheck、test、build；
- Playwright 桌面与移动端；
- Impeccable detector；
- `git diff --check`；
- 可用时进行脱敏或只读真实存档验证。

真实玩家进度 fixture 不可用时，必须明确记录“真实玩家进度解析未验证”，不得以合成测试代替真实验证结论。

## 18. 实施分层

实施时按一个重构模块完成，不在同一模块顺手改造其他一级页面：

1. 新增解析回归测试和合成 fixture；
2. 扩展规范化字段和缓存 schema；
3. 增加聚合查询、筛选和类型化 API；
4. 重构总览门厅与六个专项入口；
5. 完成关系导航、移动端和状态矩阵；
6. 完成许可、文档、自动化和视觉验收；
7. 更新路线完成记录与模块交接后停止。

不得在解析、API 和 UI 尚未形成端到端闭环时把中间状态标记为模块完成。

## 19. 回滚

- 真实存档不发生迁移，无需存档回滚；
- 新缓存是派生数据，可删除新版本缓存并由旧实现重新解析；
- API 迁移期间保留旧只读契约，前端可整体回退到旧世界数据页面；
- 元数据导入使用固定版本，回滚时删除对应生成文件并恢复 notice；
- 回滚不得覆盖用户在本模块外的现有修改。

## 20. 已知未验证项

- 当前脱敏 `level.m5.json.gz` 不包含玩家进度字段；
- 尚未用脱敏或真实玩家存档验证 Boss、高塔、地下城、油田、科技点和配方解析；
- 尚未验证压力规模 5,000 只帕鲁和 50,000 个物品槽；
- 本文档确认的是设计和验收合同，尚未实施代码、测试或构建。
